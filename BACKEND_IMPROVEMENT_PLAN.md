# План безопасного улучшения бэкенда

## Статус реализации

Выполнено без изменений PostgreSQL: отключена синхронизация Sequelize, исправлены календарные расчёты и ожидание записи отмены, фильтрация повторяющихся занятий перенесена в SQL, добавлены валидация HTTP-входа, атомарные маршруты сохранения/переноса разового занятия, открытый CORS, пагинация полных списков и unit-тесты.

Не выполнено и требует отдельного решения владельца: подключение к конкретному существующему контейнеру или Docker volume рабочей БД, модель аутентификации и выдача учётных данных. Эти пункты намеренно не угадываются, чтобы не заблокировать легитимный доступ к данным.

## Неприкосновенные ограничения

PostgreSQL уже содержит значительный объём рабочих данных. В рамках работ запрещено:

- изменять структуру таблиц `lessons` и `ext`;
- добавлять, удалять или переименовывать столбцы, индексы, ограничения, триггеры и типы;
- выполнять миграции, `sync({ alter: true })`, `sync({ force: true })`, `sequelize.sync()` или DDL-запросы;
- очищать, перезаписывать, преобразовывать или массово исправлять данные;
- запускать `docker compose down -v` для окружения с рабочей БД.

Значение `DB_SYNCHRONIZE` должно оставаться `false`. Проверки БД выполняются только запросами на чтение и после резервного копирования, выполненного владельцем инфраструктуры.

## Цель

Повысить надёжность, безопасность и производительность API, сохранив существующие таблицы, формат записей и совместимость фронтенда с текущими маршрутами.

## Этап 1. Безопасная инвентаризация

1. Зафиксировать имя действующего PostgreSQL-контейнера или Docker volume и способ резервного копирования.
2. Снять read-only метрики: число строк в `lessons` и `ext`, долю отменённых записей, время ключевых API-запросов.
3. Сопоставить все фактически используемые фронтендом маршруты с контроллерами и DTO.
4. Проверить на копии данных сценарии: создание, редактирование, отмена, недельный экран и месячные расчёты.

Критерий завершения: есть перечень используемых маршрутов и исходные метрики, при этом в БД не выполнено ни одного изменяющего запроса.

## Этап 2. Исправления логики без изменения данных

1. Сохранять ожидание `await` при записи отмены занятия — уже исправлено в `decayById`.
2. Использовать реальное число дней в месяце и корректно учитывать переход с января на декабрь прошлого года — уже исправлено в `calcMonth`.
3. Выполнять отбор повторяющихся занятий в PostgreSQL, а не загружать всю таблицу в память — уже исправлено в `getWeekNew`.
4. Проверить расчёт `repeateble/getMonth` на сценариях неполного первого месяца и месяца с будущими повторяющимися занятиями. Менять формулу только после подтверждения бизнес-правила.
5. Явно различить ответы «не найдено» и технические ошибки, сохранив совместимость фронтенда: сначала обновить клиент, затем вернуть API-коды `404` вместо текущего `400` там, где это уместно.

Критерий завершения: существующие данные не изменены, а результаты расчётов подтверждены на контрольных примерах.

## Этап 3. Контроль входных данных

1. Добавить `class-validator` и глобальный `ValidationPipe` с `whitelist: true`.
2. Описать допустимые диапазоны для `idMonth` (0–11), `idDay` (0–6), времени, длительности, стоимости и идентификаторов.
3. Включать строгую валидацию поэтапно: сначала режим журналирования, затем отклонение некорректных запросов после проверки реального трафика.
4. Не менять имена полей DTO и форматы ответов без одновременной адаптации фронтенда.

Риск: строгое включение валидации может выявить старые клиентские запросы с неверными типами. Поэтому этап требует тестирования и развёртывания через отдельное окружение.

## Этап 4. Атомарность операций

1. Заменить клиентскую цепочку `checkIsRead` → создание/редактирование на одну серверную операцию сохранения.
2. Реализовать операцию в транзакции Sequelize, не меняя таблицы и существующие строки вне целевого занятия.
3. До включения операции проверить наличие исторических дубликатов одинаковых слотов: только read-only запросом.
4. Не добавлять уникальный составной индекс, поскольку это является изменением БД и может не примениться при существующих дубликатах.

Критерий завершения: повторный запрос не создаёт лишнюю запись, а параллельные запросы имеют предсказуемый результат в пределах возможностей текущей схемы.

## Этап 5. Безопасность доступа

1. Определить модель доступа: один доверенный пользователь, несколько пользователей или интеграция с внешней авторизацией.
2. До добавления авторизации не публиковать порт `5000` в интернет; ограничить его firewall или reverse proxy.
3. CORS оставлен открытым по требованию владельца; не публиковать API в интернет без аутентификации.
4. После согласования модели внедрить аутентификацию и защитить изменяющие маршруты (`POST`, удаление, отмена, редактирование).

Критерий завершения: неавторизованный внешний пользователь не может читать или изменять расписание.

## Этап 6. Производительность API

1. Добавить пагинацию для `GET /extentions` и `GET /repeateble`, так как сейчас они могут вернуть все записи.
2. Убрать `include: { all: true }` там, где модели не содержат связей и включение не нужно.
3. Измерить медленные запросы на копии данных; оптимизировать только код запросов, не меняя БД.
4. Сохранять обратную совместимость: новые параметры пагинации должны быть необязательными, а старые маршруты — работать прежним образом до согласованного перехода.

## Этап 7. Тесты и выпуск

1. Написать unit-тесты для месячных расчётов: январь, февраль обычного и високосного года, переходы между месяцами, отменённые и неоплаченные занятия.
2. Написать интеграционные тесты API на отдельной тестовой PostgreSQL, никогда не на рабочей БД.
3. Перед выпуском выполнить резервное копирование рабочей БД владельцем инфраструктуры.
4. Развернуть контейнер бэкенда без `DB_SYNCHRONIZE` и проверить логи, healthcheck и ключевые ручки.
5. Подготовить план отката: вернуть предыдущий образ бэкенда; БД при этом не затрагивается.

## Порядок внедрения

1. Этап 1 и тесты из этапа 7.
2. Этап 2.
3. Этап 3.
4. Этап 4.
5. Этапы 5 и 6 после согласования требований к доступу и API.

Каждый этап выпускается отдельно. Если проверка не пройдена, откатывается только образ приложения; PostgreSQL остаётся без изменений.
